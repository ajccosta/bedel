An alternative to GitHub Classroom and classroom50

Run your course on GitHub, your way.

bedel signs up your students' groups, gives each group its own repository for every assignment, and enforces your deadlines to the minute. It all runs from one repository in your own organization, so every workflow, rule and form is a file you can read and change.

Groups register themselves

Students fill in a form with their student numbers and GitHub usernames. bedel checks every number against your roster, waits for each member to confirm, then creates their team and invites them.

A repository per group, per assignment

Release an assignment and every group gets a private repository with your starting files, plus an issue that emails them. Groups that register later get theirs automatically.

Deadlines enforced to the minute

Work pushed after the soft deadline counts but is marked late. At the hard deadline, the repositories become read-only. Soft deadlines can follow each class's own weekly session.

Work carries over

An assignment can start from each group's previous one, with the full history and the new starting files committed on top.

Evidence students can't rewrite

Every push is archived to a private repository, so a force-push can't hide when something happened. Reports show who pushed what, before which deadline.

Your students' data stays with you

Only student numbers ever reach GitHub, stored as encrypted secrets. Names, emails and the rest of your lists never leave your computer.

Everything is a file you can change

Hosted classroom tools give you the settings their makers chose. bedel is a repository: the workflows that run it, the rules that decide deadlines and the form students fill in are all plain files in your organization. Change one and push, and that's how your course works now.

course.json # name, group size, classes
.github/workflows/
  register.yml # when groups are processed
  deadlines.yml # when repos are locked
  assignment.yml # releasing an assignment
scripts/
  rules.py # who gets which soft deadline
  register.py # who may register, and how
  deadlines.py # locking and reports

Different deadline policy?

Soft deadlines come from one short Python function in rules.py. Give one class an extra week, count from the latest member's session instead of the earliest — it's a few lines.

Different schedule?

Every workflow is ordinary GitHub Actions YAML. Lock at a different time, add an autograder, send a report somewhere — edit the workflow.

And still get updates

A course keeps bedel as its upstream, so later fixes arrive with one git pull. Your course's own files never conflict.

bedel and GitHub Classroom

Both give every student or group a repository made from your template. They differ in who owns the machinery.

Set up a course

Six steps, about ten minutes. Run them again any time to change the course, the roster or the token.

This page has no server. It runs in your browser and talks only to GitHub's API. Your tokens stay in this tab and are forgotten when you close it. Student lists are read here, and only the student numbers (and classes) are sent to GitHub, encrypted. Prefer a terminal? git clone bedel and run ./scripts/setup.sh — it does the same.

Your course's organization

Students' teams and repositories live in a GitHub organization of their own, one per course edition. A free one is enough. Create an organization if you don't have one, then enter its name.

A token for this page

GitHub doesn't let a page create tokens, so this is the one thing you click through yourself. The link fills in everything except one field: under Repository access, choose All repositories, since the course repository doesn't exist yet. It lasts 7 days and is only for setting up.

What this token can do, and why

Organization administration: lock down member permissions (step 6). Administration: create the course repository. Contents: write course.json. Issues: create the labels. Secrets: store the roster and the bot's token, encrypted. Actions and Workflows: release assignments and regenerate the students' files. Members (read): check that you own the organization. It only reaches this organization.

The course

Students see the name. Classes are the weekly sessions soft deadlines are counted from; leave them out if your course has none.

Your students

The roster is who may register: a CSV export with a student-number column, or a plain list of numbers. Class listings are optional: one file per class with a Class: P1 (or Turno: P1) line, or one file of number,class lines. Leave both empty to keep what's already stored.

Adds 99901, 99902, … so you can register a test group with your own accounts. Set back to 0 before term.

The bot's token

The bot keeps this token to create teams and repositories and to lock them at deadlines, so it gets only that, for as long as your term lasts. Again choose All repositories: the bot creates new repositories all term. It must belong to an owner of the organization.

What the bot's token can do

Administration: create repositories and give teams access. Contents: starting files, deadlines, the push archive. Issues: announce assignments. Commit statuses: mark late commits. Workflows: starting files that contain workflows. Members: create teams and invite students. Before it's stored, the page checks each permission with a request GitHub refuses without creating anything.
